# 原生界面内存检查

下一版 MacFan 0.4.2 修复持续监测时原生界面的内存增长。原生窗口与菜单栏共用一个监测进程，无需为降低内存而减少测点、降低采样频率或关闭温度规则。早期开发版本标作 0.5.0/0.5.1，尚未正式发布；按补丁版本策略纠正后，以下历史测量仍保留当时的构建标识。

## 原因与修复

0.5.0 的 `Command` 用一个长时间运行的 GCD 工作项读取 NDJSON。Foundation 解析每帧 JSON 时产生的 autorelease 对象，直到整个工作项结束才释放；监测进程持续运行，临时对象也持续累积。主线程忙时，逐帧排队的界面更新还会额外保留旧快照。

修复后的实现每次读取后排空 autorelease pool。每段连续的成功 `sample` 事件只保留最新待显示快照，控制、错误、恢复和结束回执仍按原顺序交付，后续快照不会越过这些回执。无效帧最多报告一次协议错误，超过 1 MiB 的帧在解码前拒绝；跨读取的超长帧丢弃到换行，之后仍可读取真实的恢复回执。

## 本机证据

2026-10-19，Apple M4 / macOS 15.5：旧版界面运行约 100 分钟后，物理内存占用约 1.27 GB，持续增长约 9.8 MiB/分钟；同一时间监测子进程约 20 MB，未出现相同增长。界面大部分分配已被系统压缩或换出，只看 RSS 会低估占用。

使用同一份 255 测点快照进行显式模拟回放，先预热 100 帧，再加速回放 5,000 帧。消费回调额外延迟 2 ms，两个检查点均保持生产进程和读取工作项存活，测量主线程回调及临时对象释放后的 `TASK_VM_INFO.phys_footprint`：

| 传输实现 | 预热后 | 5,000 帧后 | 增长 | 测量期间峰值 |
| --- | ---: | ---: | ---: | ---: |
| 0.5.0，`3d66014` | 32.90 MB | 978.91 MB | 946.01 MB | 980.34 MB |
| 0.5.1 修复后的传输 | 10.27 MB | 16.88 MB | 6.60 MB | 18.43 MB |

这里的 MB 为十进制。回放覆盖实际 `Command` 与 `Snapshot` 解码，验证控制回执顺序、失败采样不被合并、最终采样先于结束回执，并检查峰值与稳定占用的增长均小于 64 MiB。回放没有启动 Helper 或写入真实风扇；它是加速数据回放，不等同于相同时长的真实界面运行。

## 重现与回归

macOS 上的 `python3 -m unittest discover -v` 自动执行 1,000 帧内存回归。完整对比可运行：

```sh
python3 scripts/test-native-memory.py \
  --output-dir artifacts/native-memory \
  --baseline-ref 3d6601442f85896021bda8bed30a87a244f34343
```

默认使用明确标记的模拟 255 测点数据。`--snapshot PATH` 可读取实机采集的快照并仅用于模拟回放，输出会记录输入和源码 SHA-256。对比会报告旧实现超出预算，最终退出码由候选实现的内存和事件检查决定。脚本有 1,280 MiB 物理内存紧急上限，避免回归耗尽系统内存。

安装后的真实应用另行检查：主窗口、菜单栏和关闭窗口后的后台监测保持更新；采样物理内存而非虚拟地址空间，记录运行时间与进程身份。真实温度监测、模拟控制回归、Helper 兼容性和硬件调速验证分别报告。
